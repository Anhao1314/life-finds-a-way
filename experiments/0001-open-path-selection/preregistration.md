## 0. 摘要

在模型、工具、任务、资源和权限边界完全相同的条件下，比较三种路径指导方式对独立验收任务成功率的影响：A 组基本目标 Prompt、B 组详细施工 Prompt、C 组 LFAW 契约 Prompt。12 个真实任务 × 3 组 × 2 次独立重复，最多 72 次运行。主要终点只有一个：由独立验收机制判定的任务成功；主要比较为 C 相对 B 的任务级成功率差。

## 1. 研究问题

在模型、工具、任务、资源和权限边界相同的情况下：

1. **Q1（主）**：LFAW 任务契约（C）是否比人类预先指定详细实现路径（B）带来更高的独立任务成功率？
2. **Q2（必须保留）**：LFAW 任务契约（C）是否比简单目标 Prompt（A）带来**额外**收益？
3. **Q3（条件）**：如果成功率发生变化，成本、工具调用、人工干预和无效投入如何变化？

**为什么 Q2 必须保留：** 如果 C 只优于 B 却不优于 A，结果只能支持「减少路径控制可能有用」，不能支持完整 LFAW 契约（质疑预设、最小判别实验、换路纪律、证据选择）有额外价值。没有 A 组，B vs C 的任何差异都会被误读成对整个契约的背书。

## 2. 假设与可能推翻假设的结果

| 编号 | 假设 | 可能推翻假设的结果 |
| :--- | :--- | :--- |
| H1 | 在路径不确定性高的真实任务上，C 的任务级成功率高于 B。 | C ≤ B：详细施工 Prompt 并不比 LFAW 契约差，甚至更好。 |
| H2 | C 的任务级成功率高于 A，即超出「只给目标」的额外收益真实存在。 | C ≈ A：额外收益不可区分，完整契约的价值主张不成立（只能支持更弱的「开放路径」主张）。 |
| H3 | 若 H1/H2 成立，C 的成本结构不同：更多探索性投入，但不显著高于 B 的返工成本，且换路/停止行为更多。 | C 成功率更高但成本显著更高且无效率信号；或 C 的行为指标与 A 无法区分。 |

允许出现「方向不一致」（例如 C 在调试类任务优于 B、在功能类任务不优于 B）——如实报告，按第 8 节规则归入 `INCONCLUSIVE`，不得拆开只报有利子集。

## 3. 实验组设计

### 3.1 共同任务事实（三组逐字一致）

每组收到完全相同的任务事实，来自 [`tasks.yaml`](./tasks.yaml) 的 `real_user_problem`、`starting_state`、`tools_and_resources`、`permission_boundaries` 四个字段，原样注入 [`prompts/common-core.md`](./prompts/common-core.md) 的 `{{TASK_FACTS}}`：

- 用户问题；
- 当前基线；
- 可用资产；
- 工具与资源；
- 权限和安全边界；
- 可公开提供的验收目标。

三组**只能**在路径指导方式上不同（见 3.3 与 [`prompts/`](./prompts/) 四个文件）。

### 3.2 组定义

| 组 | Prompt 模板 | 内容 |
| :--- | :--- | :--- |
| **A · 基本目标** | [`prompts/A-basic-goal.md`](./prompts/A-basic-goal.md) | 共同任务事实 + 完成任务并报告结果。**不**加入候选路径、最小证伪实验、换路和证据选择等 LFAW 指导。A 组仍包含完整的安全与权限边界（来自共同任务事实），不为了制造对照而取消安全约束。 |
| **B · 详细施工** | [`prompts/B-prescribed-path.md`](./prompts/B-prescribed-path.md) | 共同任务事实 + 一份在实验前写好的、合理且可信的人类实现方案（`tasks.yaml` 的 `b_prescribed_path`）：推荐技术路线、实现步骤、模块或修改顺序、指定验证步骤。**B 组方案不得是故意愚蠢或不可行的稻草人**——它们应代表有经验的开发者在看到结果之前真实会写出的施工说明（第三方回归任务的 B 方案由设计者在预注册时撰写；ClaimLedger 任务的 B 方案直接来自作者已公开发布的设计文档与 issue，见 §12 局限）。 |
| **C · LFAW 契约** | [`prompts/C-lfaw-contract.md`](./prompts/C-lfaw-contract.md) | 共同任务事实 + LFAW 契约要素：可以质疑预设方案；先核对真实基线与瓶颈；自主选择最有希望的路径；必要时优先实施最小判别实验；不为了完成计划维持错误路线；在既定权限内自主推进；最终报告事实、证据、失败、成本以及接受、回退、转向或停止建议。 |

### 3.3 执行方式

- 每次运行使用**独立新会话**，不共享其他组的过程、结果或记忆。
- 每个 Agent 只读取自己组的 Prompt；不读取其他组 Prompt、评分材料或本文件。
- 隐藏验收材料（上游修复 diff、验收脚本、评分细节）**绝不**出现在任何组 Prompt 中（信息流见本目录 [README](./README.md)）。
- 为防止第三方回归任务的公开修复记录污染结果，所有组统一禁止运行期网络访问（见共同任务事实的权限边界）；依赖在运行前一次性安装并冻结。

### 3.4 已登记的设计决策（防止事后争议）

- **统一交付格式在共同任务事实中**（改动清单、运行方式、完成陈述），三组一致；C 组的证据/成本/建议报告是**附加**要求，不是三组唯一差异的来源。主要终点判据只依赖统一交付格式即可执行的部分。
- **B 组偏差政策**：B 要求按方案的技术路线与步骤顺序实现；某一步确实无法执行时，停止并如实报告原因，不静默换路。这是「详细施工 Prompt」条件的操作化，写在此处供评审，不是执行时再决定。
- **C 组的「申请批准」在实验语境下操作化为**：停止并在最终报告中说明需要什么授权。

## 4. 任务集

### 4.1 纳入标准

- 来自真实代码库或真实项目问题（公开可核查的 issue / 设计文档 / 用户报告），不得为了迎合 LFAW 编造；
- 具有真实的路径不确定性：存在不止一条合理路径，或根因不能从现象直接读出；
- 独立验收可判定：可脚本化测试或预登记的可观察判据，不依赖设计者主观判断；
- 执行环境为本地：不需要付费 API、GPU、生产部署或网络访问；
- 规模可控：预计单次运行可在冻结的超时内完成。

### 4.2 排除标准

- 根因或修法唯一且机械（纯「答案唯一的单元测试修复」不做主任务）；
- 验收依赖设计者主观品味；
- 涉及真实用户数据、生产系统或不可逆操作；
- 来源不可核查，或执行前无法复现基线且无法修复该缺口。

### 4.3 任务集概览

12 个任务全部登记在 [`tasks.yaml`](./tasks.yaml)，每条含：稳定 `task_id`、来源仓库与固定 commit、真实用户问题、起始状态、可用工具与资源、权限边界、独立验收方式、任务类型、选择理由、B 组预先指定的合理实现路径、预计成本与可能的失败模式。

### 4.4 执行前义务（基线复现）

每个任务在首次运行前，验收方必须在固定 base commit 上：

1. 复现起始状态（`tasks.yaml` 的 `starting_state` 描述的现象或基线）；
2. 确认隐藏验收判据在「未修复」状态下**判为失败**（即验收能区分修复与未修复）；
3. 记录复现结果。无法满足第 2 点的任务从本批次移出，并在 amendments 中记录（发生在查看任何运行结果之前）。

## 5. 重复与随机化

- 12 个任务 × A/B/C 三组 × 2 次独立重复 = **最多 72 次运行**。
- **实际执行前必须由仓库所有者确认模型与预算。** 本预注册不因写下 72 次运行而自行执行。
- 每个任务内的组执行顺序已随机化并冻结：种子 `20261028`，Python `random.Random(20261028)` 对每个任务的两次重复各做一次独立洗牌。顺序表见**附录 A**；再生成命令随表给出，可逐字节复核。
- 运行前必须冻结并登记（附录 B）：模型、模型版本、温度、工具集、超时、资源与预算限制、环境规格。冻结后任何变更走 amendments。

## 6. 主要终点

**主要终点只有一个：由未参与实现与调参的独立验收机制判定的任务成功。**

- 验收机制在运行前脚本化并冻结（判据来源：`tasks.yaml` 的 `independent_acceptance`；Gold 参考为上游修复 diff，仅验收方可见）；
- 验收方不参与任务设计调优、不阅读运行过程、只依据统一交付物与验收脚本判定；
- 验收方对组别标签可用（本设计未做验收盲化，见 §12 局限与缓解）。

**主要比较：C 组相对 B 组的任务级成功率差。**
**重要补充比较：C 组相对 A 组的任务级成功率差。**

### 6.1 任务级聚合（重复不夸大样本量）

重复运行**不能**当作更多独立任务来夸大样本量。分析以 **task 为配对单位**：

- **任务级成功（主指标）**：该组在该任务的 2 次重复中**至少 1 次**通过独立验收；
- **任务级稳定成功（敏感性指标）**：2 次重复**全部**通过；
- 重复间一致性单独报告，用于反映运行稳定性，不参与主要判定。

配对比较定义：对每组对照（C vs B；C vs A），统计 12 个任务中 C 成功而对照失败的任务数（胜）与反之的任务数（负），**净胜任务数 = 胜 − 负**。

## 7. 次要指标

- 总 Token 与 API 成本；
- 工具调用次数；
- 墙钟时间；
- 人工干预次数；
- 路径放弃、换路和停止行为；
- 权限或边界违规；
- 失败类型与 `INCONCLUSIVE` 数量。

**严重权限或边界违规不能被更高任务成功率抵消**：严重违规（越权联网、调用付费 API、修改冻结材料、破坏基线数据、超出沙箱写权限）的运行**计为该次任务失败**并单独报告，触发对所有关联运行的人工审查；审查结论记入报告，不静默剔除。

## 8. 探索性结果的判定规则

本实验是单批次小样本探索性设计，**不能产生「LFAW 已被证明普遍有效」的结论，最高结论为 `PROMISING`**。预注册解释规则如下（`净胜任务数`定义见 §6.1）：

| 判定 | 条件（全部满足） |
| :--- | :--- |
| **PROMISING** | ① C 相比 B 至少多完成 2 个任务级成功（净胜任务数 ≥ +2）；② 相对 A 也显示额外收益（净胜任务数 ≥ +1）；③ 无严重边界违规；④ 成本处于预注册可接受范围（阈值在附录 B 冻结）。 |
| **INCONCLUSIVE** | 方向不一致、样本不足、成本与收益冲突，或无法区分 C 与 A。包括：C−B 净胜为正但不足阈值（+1）；C−B 与 C−A 方向矛盾；任务级（≥1/2）与稳定级（2/2）指标方向相反；成本越界但成功率达标等。 |
| **NOT_SUPPORTED** | C 不优于 B（净胜 ≤ 0）；或 C 只优于 B 但不优于 A（C−B > 0 且 C−A ≤ 0），无法支持完整契约的额外价值。 |

**`NOT_SUPPORTED` 只表示本次设计未支持该方法，不等于证明方法永远无效。**

**操作化说明（登记，不替换规则）：**「至少多完成 2 个任务级成功」被操作化为净胜任务数 ≥ +2（胜减负）；若理解为「胜的个数 ≥ 2 且不允许负」会更严格。本设计采用净差口径，因为 12 个配对任务里两组互有胜负是正常形态，净差更接近「多完成」的字面含义。对阈值的任何修改必须在查看结果前以 amendment 记录。

## 9. 运行失败、超时与基础设施故障

- **超时**：达到冻结超时的运行记为该次失败（`FAIL_TIMEOUT`），不延长重跑；
- **基础设施故障**（模型提供方中断、沙箱崩溃、环境损坏）：允许**一次**重跑，两次尝试全部留档于运行清单；重跑仍失败则该次记为 `INCONCLUSIVE_RUN`，对应任务-组进入该次重复的失败计数；
- **不接受**任何「这次没跑好再悄悄跑一次」：每次调用模型都有清单记录，清单先于分析存在；
- 某任务-组两次重复均因基础设施失败时，该任务在该对照中按 `INCONCLUSIVE` 处理并在报告中单独说明。

## 10. 数据与结果纪律

1. **原始结果与派生分析分开保存**：原始会话转录、工具调用日志、清单进 `runs/`（执行时创建）；任何聚合、图表、结论进 `analysis/`（执行时创建）。派生数据必须可由原始数据加冻结脚本重算。
2. **不得为了得到 PASS 修改历史 Gold、测试、阈值或原始日志**：验收判据一经冻结即不可修改；上游修复 diff 是只读 Gold 参考。
3. **负面结果和 `INCONCLUSIVE` 不得删除**，与 `PROMISING` 同权重报告。
4. **Amendments**：冻结后（首运行开始前或后）的任何修改——任务替换、参数变更、规则澄清——必须逐条追加到**附录 C**，标明日期、内容、动机，以及**是否发生在查看任何运行结果之前**。查看结果后的修改不得改写已登记的判定规则。

## 11. 后续独立复验所需的条件

他人复验本实验需要：本预注册与 `tasks.yaml`、`prompts/` 的冻结版本（commit SHA）；附录 B 的冻结参数；附录 A 的随机化种子与顺序表；运行清单与原始转录存档；验收脚本及其在 base commit 上的失败复现记录。满足以上条件时，复验应能以不同执行者、（可选）不同模型重跑并独立完成验收。

## 12. 局限（预注册时如实登记）

- **小样本**：12 个配对任务、每组 2 次重复，统计功效低；只能产生方向性证据（最高 `PROMISING`），不能估计效应大小。
- **任务选择偏倚**：任务由本仓库作者挑选。任务集以第三方库回归调试为主（7/12），性能与结构类偏少；ClaimLedger 占 4/12，存在来源集中。
- **作者偏倚与熟悉度**：作者对 ClaimLedger 极度熟悉，其 B 方案直接取自作者自己发布的设计文档——这使 ClaimLedger 任务的 B 组特别强，可能**低估** C 相对 B 的差异；同时作者对 LFAW 的认同可能渗入任务措辞。
- **Prompt 长度与结构差异**：C 组 Prompt 最长，B 组次之。差异无法完全归因于「指导方式」本身。
- **验收未盲化**：验收方可获知组别。缓解：验收以预冻结脚本为主，主观裁量最小化；脚本判定不足的任务（LF012）在所有者确认验收方式前不运行。
- **公开修复可见性（污染）**：第三方任务的修复已公开，模型可能背过。缓解：运行期禁网、本地固定 commit；但无法排除模型参数记忆，结果解读必须保留此混淆。
- **单模型、单执行环境**：结论仅对冻结的模型与环境成立，不外推。
- **探索性阈值**：PROMISING 阈值（净胜 +2 / +1）无统计功效计算支撑，是预注册的约定而非功效分析结果。
